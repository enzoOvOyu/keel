# Codex 开发入口

基准：PRD.md v3.0.3、DESIGN-SYSTEM.md v3.0.3。更新：2026-10-23。
本文只负责文档导航、跨文档处理口径和任务执行方式，不新增产品需求，也不证明功能完成。

## 1. 先找到当前事实，再选任务

1. 按根目录 [AGENTS.md](../AGENTS.md) 读取 [HANDOFF](HANDOFF.md)、[DEPLOYMENT](DEPLOYMENT.md)，核对 Git 差异与运行版本。保留已有修改。
2. 在 [实施计划](../IMPLEMENTATION-PLAN.md) 选完整工作包，确认依赖和退出条件；在 [追踪矩阵](requirements-traceability.json) 找 FR、WP、验收 ID。
3. 阅读下表对应章节。只读任务相关内容；历史审查不作为日常必读材料。
4. 以现有实现为起点，交付 API、服务、页面及证据的完整链路。发现缺失依赖先补依赖，不能用手动赋成功状态替代。

用户后续明确约束（2026-10-23）：前端统一Intel One Mono等宽字体，已同步DESIGN-SYSTEM §2.2与字体令牌。该要求覆盖原Inter/JetBrains字体配置；中文缺失字形系统回退。

2026-10-25用户追加安排：下一次涉及前端改动时，先基于已接入的shadcn/ui共享基础（HANDOFF §23）完成组件库剩余接入与页面统一，再将全局字体调整为更好看的等宽字体；没有合适选型时采用RunPod实际使用的字体，实施时核对来源、授权、字重与中文回退，并同步正式设计令牌及实际浏览器验证。此最新安排允许届时替换原Intel One Mono选型；当前字体尚未修改，本轮Agent后端收尾不提前开展该前端任务。

用户当前指令优先。业务范围、判据、授权数据域以 PRD 为准；视觉、布局和组件交互以 DESIGN-SYSTEM 为准。PRD 明确委托给架构的状态机（如 Execution）仍由相应架构章节定义。下游文档只实现、分解和验证这些契约，不反向改需求。

## 3. FR-0 的开发顺序和业务顺序

**业务上 FR-0 是服务器交付的第 0 步；软件开发仍先具备认证、项目、可靠执行、介质、参数和型号能力。** 两者不能混用，也不能把 Kea 当成整个软件底座。

| 链路 | 工作包与必须产物 |
|---|---|
| 统一资产入口 | WP-1.15 → WP-1.16：一包原子导入双域物料、稳定身份、型号/工程校验、问题清单；字段格式只引用 PRD 附录 A |
| 最小开通 | WP-1.17：N-S2 最小管理地址/命名/批次规则、N-S3 环境逐项自检、Kea staging/commit、239/143 身份反查、批准的隔离/管理引导、九步时间线、失败重试和凭据错误分类；不安装生产网络配置 |
| 预校验与生产配置 | WP-2.14 → WP-2.15：N-S5 网络侧预校验及采集/证据接口；Golden → Doublecheck → 备份/diff/计划 → Batfish/预演 → 审批 → PushJob → 复采 |
| 健康、无损与治理 | WP-3.14 → WP-3.15：BGP/DDM/PTP 健康、LL-01～07、日志/降级、规则版本/作用域/审批/dry-run |
| 联合验证与归档 | WP-4.10：网络证据贯穿 G2/G5/G6、规模压测、基线导出与 CMDB 归档、第三方适配器及 PoC 包 |

依赖全集以实施计划 §3 和追踪矩阵为准；表中顺序只是 FR-0 阅读路径。日常按依赖闭包推进可用前置已具备的完整功能，可跨 P 层并行；阶段签署仍须满足全部出口。不能跳过实际依赖，也不能等待不相关阶段项或硬件 PoC 才开发后续软件。

执行前牢记四条边界：

- N-S4/ZTP 完成只证明最小管理引导；**NP-2 还要求最近 Golden 结论满足 PRD §1.5.3**，不能由 `managed` 单独推导。
- N-S5 只做网络侧预校验，未装机服务器端口保持 pending；**NP-3 由 G2 三方比对确认后产生**，G3 消费。启动 G2 检查 NP-1/NP-2/NP-4，G5/G6 再检查 NP-5/NP-6。
- Kea 负责 DHCP 配置/租约与引导选项；Kestra 是自研作业模型与执行视图的参考。网络任务复用同一 Execution/Runner/审计，不能再建旁路执行器。
- 网络指标缺失、能力不可得或规则停用，显式 `unknown` 并记录降级；不能补零、判 normal 或以 sim 结论更新真实设备就绪状态。

## 4. 完整功能交付与可修改模块

实施方法以 [计划 §3](../IMPLEMENTATION-PLAN.md#3-任务分解按阶段编号-wp-xy-供验收映射) 的六个功能块为当前入口。直接复用已有 P1/BOM/ZTP，按差额补齐，不反复重做已经有效验证的链路。每次把契约、持久化、权限、API 与 DS 页面一起交付，避免长期只完善后端仿真而看不到产品进展。开始任务时在当前工作记录中写清以下六项即可：

| 项目 | 内容 |
|---|---|
| 范围 | WP + FR 子条 + 验收 ID，写明本次完整能力 |
| 前置 | 所需依赖、基线/型号/介质/权限版本；缺口与处理方式 |
| 契约 | API/事件、持久化与状态变更、授权范围和幂等/并发语义 |
| 页面 | DS 页面/组件、数据协议、真实/空/失败/未知状态；项目作用域与布局 |
| 验证 | 正向链、关键拒绝/失败恢复、证据位置；按影响执行必要检查 |
| 交接 | 完成/剩余、源码提交与运行版本、下一完整工作包 |

模块职责和修改入口见 ARCHITECTURE §1.2：业务判定/用例、存储、HTTP、UI、设备适配分别承担职责，现有目录逐步调整，不先全仓重构。NOS 命令解析、能力矩阵、Kea、凭据来源可独立替换；endpoint/CA/超时/并发/重试由配置及批准策略提供。PoC 发现差异先定位到适配器、能力数据或规则，回录脱敏原始样本；业务判据变化再同步用例与设计，不能靠放宽门禁兼容设备。

框架连通性阶段交付可替换适配器、必要契约 fixture、真实持久化/API/权限链路及页面；真机 PoC 独立记录。mock 仅放在外部硬件/协议边界，不扩展专门的手动“推进成功”产品流程。fixture 必须有版本/来源/能力缺口，不能人为输入 PASS 后声称实际设备已通过。

## 5. 完成状态与证据

追踪矩阵 `planned` 表示尚无完成证据；`partial` 表示有部分实现及明确剩余项。只有对应验收范围已执行并满足判据，才提升其完成状态。设计检查通过、单测通过、隔离服务连通、部署健康、浏览器交互和硬件 PoC 是不同证据。

验证按下表执行，保留原业务与安全判据：

| 时点 | 执行范围与停止条件 |
|---|---|
| 纯文档修改 | 一轮设计结构/引用/依赖检查与语义复审；不启动设备仿真或代码全套 |
| 完整功能块开发 | 必要关键判定单测、外部协议/契约连通；API/数据库/权限/页面完成后集中做一轮集成。通过且没有具体剩余风险即转下一功能 |
| 失败修复 | 定向复验失败及受影响链；安全/数据/准入严重缺陷按验收策略执行所需全链回归 |
| PR/阶段交付 | 仓库规定的完整检查/CI；同一版本已通过的有效结果复用，不再手动重复同一套 |
| 规模/硬件验证 | 在计划规定的规模环境/PoC 窗口运行，记录真实连接与测量；未执行标 NOT_RUN，不阻止无依赖的日常软件开发 |

新增改动、依赖变化、测试失败或明确未决风险才扩大重测范围。禁止每加一个字段就重跑同一完整模拟链、重复构建相同版本或新增一套相同测试工具；进展以可用能力与已消除缺口衡量。

完成后只更新 HANDOFF 当前快照与受影响追踪行，旧过程归档。不在 PRD、架构和部署说明里反复维护同一版本号、下一步或“已完成”宣言。
