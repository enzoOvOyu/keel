# A4 型号草稿审核与不可变发布

本功能接续 WP-1.12，覆盖 PRD FR-14.1/14.3/14.4 与 DESIGN-SYSTEM §4.12d 的完整规格审核发布路径，以及 ACCEPTANCE F-14.1/F-14.2 的部分版本保护。PRD 的 FR-14.4 扫描导入与 ACCEPTANCE 的 F-14.4 G1 门禁是不同编号；本轮不声称 G1 或整个型号库验收完成。

## 本轮行为

原发布弹窗只携带扫描草稿的硬件规格/槽位，遗漏预期拓扑、面板布局、BOM期望和角色方案；重复导入返回的草稿也缺槽位。本轮统一保存、返回和审核以下字段：

- `hw_spec`、`expected_topology`、`capability_matrix`；
- `panel_layout`、`bom_expect`、`default_role_plan`；
- `slots`（槽号、PCIe槽、期望网卡、面板端口和默认角色）。

扫描仍只创建草稿。人工逐项核对、可修改后调用原版本发布接口，创建新的不可变版本；草稿不会自动发布或自动升级设备绑定。发布页完整显示全部JSON规格，槽位沿用表格输入；已发布历史可展开读取完整规格。面板可视化/角色覆盖消费尚未在此实现。

草稿复用完整返回元数据与槽位，使用同一事务完成当前授权、型号定位、去重及审计。扫描明确声明 `hw_spec.kind` 时核对稳定身份，网络设备扫描须有能力矩阵；不能把交换机默认为服务器，也不能复活同名退役型号。项目入口只能写本项目型号/草稿，公共全局型号的已发布版本仍可读，未发布全局草稿不向项目接口公开。Viewer 保留读取权限，页面不显示发布/废弃动作，服务端仍独立复核权限与CSRF。

## 版本与草稿前置条件

`POST /api/v1/projects/{id}/models/{modelId}/versions` 新增两个可选输入：

```json
{
  "expected_version": 2,
  "source_draft_id": "32-character-draft-id",
  "hw_spec": {},
  "expected_topology": {},
  "capability_matrix": {},
  "panel_layout": {},
  "bom_expect": {},
  "default_role_plan": {},
  "slots": []
}
```

示例只说明字段，不是硬件配置。审核页始终提交打开时观察到的 `expected_version`，新建型号为0。服务端锁定型号后核对当前版本，陈旧返回409 `MODEL_VERSION_CONFLICT`，不创建新版本或成功审计；用户须刷新后重新审核。若提供 `source_draft_id`，必须同时提供版本条件，草稿须仍存在且属于该型号。审核允许人工修改草稿内容，审计保留来源草稿ID、基准版本与最终摘要。

已有工具/BOM夹具省略这两个输入时保留原追加版本语义，不引入隐式覆盖；不能把这些旧调用声称为具备审核页的乐观并发条件。这里也没有新增网络重试成功重放的发布幂等契约；页面在网络结果不确定时通过版本条件避免静默重复追加，需读取历史确认。

废弃草稿路径现在同时校验URL的 `modelId`、`draftId` 和项目归属，不能通过同项目另一个型号的URL废弃其他草稿。草稿在发布后仍可手动废弃，发布历史和审计不随之删除。

## 内容身份和数据库保护

- 新内容摘要统一将省略的JSON对象/槽位与空对象/数组视为相同，槽位按槽号排序；不修改调用者传入的槽位顺序。默认角色、拓扑、面板、能力和BOM期望均参与摘要。
- 现有版本/草稿的存储摘要不重写。重新扫描时按最新版本的实际完整内容计算比较摘要，并可按完整JSON识别旧格式摘要的等价草稿，避免因 `null`/`{}` 或槽位显示顺序产生伪重复。
- 新迁移 `040_model_publication.sql` 为草稿增加能力矩阵；禁止UPDATE/DELETE已发布版本及其槽位。槽位仅允许在创建对应版本的同一事务中组装，提交后不能追加。既有发布接口仍在一个事务中写版本、槽位和审计。
- 新版本与退役操作不改 `ProjectAsset.model_version_id`；历史引用不自动跟随最新版本。040 迁移的实际部署情况见 HANDOFF 最新发布记录；源码构建本身不等于已部署数据库保护。

扫描观测不能直接作为验证自身通过的独立规格；审核页明确提醒来源核对。外部规格真实性、签名和真实采集兼容性仍须各自证据，fixture不冒充厂商或硬件验收。

## BOM 消费已发布的服务器硬件期望

逐实体 BOM 在只读预检及提交事务内，按 `server/servers.csv.model_ref` 的固定版本读取 `bom_expect.nic_count` 和 `slots`；创建新版本不改变旧包的校验结果。`nic_count` 是物理 NIC 部件数，发布/扫描草稿只接受非负整数。槽位使用 `slot_no` 的十进制字符串或精确 `pcie_slot`；`onboard` 也必须由型号显式声明，不通过排序猜测。存在槽位定义时，逐项检查缺失、重复、未声明/歧义位置，并用 NIC 绑定型号的正式名称比对 `expect_nic_model`，不相信用户填写的 `sub_type`。

差异产生 BLOCK，定位到文件、BOM 行号及字段，附 `model_version_ref`、`expected`、`actual`。预检拒发提交令牌，提交仍重新校验且拒绝写入。页面及导出 CSV 保留这些明细。BLOCK 不形成已提交包，因而无需为历史问题表追加列；旧包问题仍按原字段读取。

未声明数量或槽位的旧型号分别返回 `model_nic_count_unverified` / `model_nic_slots_unverified` WARN；允许兼容导入不能视为硬件期望核验通过。只有 MAC 的宽表不能证明物理 NIC 数量、型号及槽位：绑定型号存在任一 NIC 硬件期望时，以 `legacy_nic_inventory_unverifiable` BLOCK 要求改用逐实体 BOM；不把一条 MAC 当作一张真实网卡。宽表问题行号保留源 CSV 行号。

本块不采集硬件、不执行 G1，不从 BOM 自行生成型号期望；其他部件规则、面板布局迁移等仍按相应阶段继续，不能据此签署整个 FR-14/WP-1.12/P1。


## BOM 永久 MAC 前缀规则

服务器型号可显式声明 `bom_expect.mac_prefixes`，例如 `["aa:bb:cc", "00:11:22"]`。这是 1–256 个不区分大小写的三字节 OUI 白名单，拒绝空数组、null、重复项、通配符及不完整前缀；省略表示未声明规则，兼容旧版本。人工发布和扫描草稿使用相同验证，不由 BOM 内容反推预期，不把观察值当独立规格。

逐实体包预检和提交复核共享物料写入的父子解析结果，按所绑定的不可变服务器版本核对该机 NIC 汇总 MAC 及服务器端口的逐口永久 MAC。支持解析器已有的 SN、行号、UID 引用；不把交换机端口套入服务器规则。NIC 汇总和逐口事实原有交叉校验继续执行。创建新型号版本不修改旧包绑定，已有历史包不重写。

不匹配返回 `model_mac_prefix_mismatch` BLOCK，携带文件、源行、mac 字段、固定型号版本、白名单与实际 MAC；页面差异及 CSV 使用已有展示。预检不发令牌，提交事务重新计算，不能用伪造的格式有效令牌绕过。宽表只验证其提供的永久 MAC，保留 CSV 原行号；仍不能证明物理 NIC 数量、槽位或型号。声明规则但未提供永久 MAC 时返回 `model_mac_prefix_unverified` WARN，不能据此报告已核验。无数据库迁移，不扩展硬件采集、G1 或型号显式升级。


## GPU 数量与型号期望

沿用硬件规格字段 `hw_spec.gpu_count`（非负整数，可为0）和 `hw_spec.gpu`（GPU 型号的正式名称，1–120字符，不接受首尾空白），例如 `{"gpu_count": 8, "gpu": "B300"}`。这两个字段分别可选；省略不等于推定0张或接受任何型号的验证结论。发布版本及扫描草稿共用校验，null、字符串数量、负数、小数、空型号等400。扫描仍先产草稿，经独立规格核对后人工发布；不由待导入BOM生成验证自身的期望。

BOM 服务器绑定固定版本的 `hw_spec`。按其 SN、BOM 行号或已登记机器 UID 归集 `category=gpu` 的物理部件，数量不符返回 `model_gpu_count_mismatch`；正式 GPU 型号身份的名称与期望不符返回 `model_gpu_type_mismatch`，不信任部件 `sub_type`。每个 GPU 的 `model_ref` 仍须是本项目可见、类型正确的已发布版本，沿用已有作用域/退役引用门禁。问题携带源文件、行、型号版本、期望、实际；预检不发提交令牌，提交事务重新校验。GPU 不进入 NIC 数量和槽位比较。

旧服务器版本未声明 GPU 期望时保留兼容；只声明 GPU 型号而没有库存（或明确数量0）时返回 `model_gpu_type_unverified` WARN，不能报告型号已核验。宽表仅提供 MAC，无法证明物理 GPU 库存：声明任一 GPU 期望时 `legacy_gpu_inventory_unverifiable` BLOCK，要求使用逐实体包。数量0也必须有能表达GPU物料清单的逐实体包，不能从MAC表推断没有GPU。

新版本不自动改变旧包和设备绑定。此增量没有迁移、不采集硬件、不实现G1或显式型号升级；独立fixture的功能验证与真实GPU到货/拓扑验证分别记录。


## 全局型号管理与项目引用

平台管理员通过 `/admin/models` 管理全局公共型号；对应 `/api/v1/admin/models` 提供列表、身份创建、草稿导入/列表/废弃、版本列表/发布和退役八项操作。使用项目型号相同的服务、事务、独立审核提示、完整规格编辑、观察版本前置条件和不可变历史，不另建发布流程。旧 `/api/v1/models` 保留全局只读列表，并明确仅平台管理员可调用；它不列举项目私有型号。

全局入口的作用域固定为 global。全局入口访问项目型号、项目入口修改全局型号，即使调用者是平台管理员也拒绝。项目成员仍通过自己的项目读取共享版本；项目页将全局型号标为“全局共享 · 仅可读取”，隐藏发布/退役/草稿写操作，且不暴露全局审核草稿。项目 Admin/SRE/Viewer 均不能调用全局管理API或页面。全局列表、版本及草稿读取在服务层也要求平台管理员；鉴权与CSRF仍按共享网关规则执行。

全局与项目型号可以同名，按现有scope唯一性区分。BOM继续固定已发布版本，发布全局新版本、退役全局型号均不自动升级项目设备。退役后历史可读，禁止新发布和新导入；本增量没有数据库迁移或显式绑定迁移/G1实现。全局管理变更使当前用户的私有查询失效，刷新项目共享列表；审核弹窗和查询缓存仍按项目/null全局范围隔离。


## 计算托盘的 BOM 绑定

`server/servers.csv` 的物理机器可绑定 `server` 或 `compute-tray` 型号，兼容 PRD 对 GB300 计算托盘的独立建模；仍拒绝 `rack`、`switch` 或部件型号作为机器型号。`bom_item.category=server` 是机器资产类别，硬件层级保留在绑定版本所属型号的 `kind` 中，不把机柜聚合数量当托盘或GPU数量，也不固定每节点8张GPU。

逐实体包和宽表按相同的可见、active 型号边界解析计算托盘；NIC数量/槽位/正式型号、GPU数量/正式型号与MAC前缀仍读取固定版本。数量和布局差异不能因kind=compute-tray而跳过。发布新版本不改旧BOM或设备绑定，GPU/NIC使用同一机器UID归属；机柜级层级导入和真实托盘操作不在此增量内。

只有MAC的宽表能识别计算托盘型号，却不能证明其GPU或NIC物理库存；有此类硬件期望时仍BLOCK，保留固定版本、CSV原行、期望/实际和问题导出。型号编辑器及列表的计算托盘类型使用正式中英文标签。没有新增数据库迁移、API路径或G1/拓扑实现，fixture验证不代表真实GB300硬件验收。


## 槽位标识冲突防护

BOM 的 NIC 槽位支持槽号或 PCIe 位置两种引用，因此每个版本内这两类标识必须唯一指向一个物理槽位。重复 PCIe 位置、PCIe 位置与另一槽位的十进制槽号重叠，均在扫描导入和发布时返回400 VALIDATION_ERROR；PCIe 位置不能有首尾空白。同一槽位使用自己的十进制槽号作为 PCIe 位置允许，01等标签按原字符串识别，不做数值猜测。不同槽位仍可使用相同网卡型号和默认角色。

编辑器在发出发布请求前显示具体冲突标识，保留输入供修正。项目与全局入口共用服务校验，失败不创建自动型号、草稿或版本，也不消费已有草稿。历史不可变版本及其设备绑定不被修改；历史中的歧义仍由既有 BOM 校验拒绝。本增量没有数据库迁移，不代表面板预览、项目角色覆盖或G1已完成。


## 版本绑定的面板预览

`panel_layout.layout_v1` 描述独立规格登记的物理位置，不来自BOM端口排序或待验采集数据推断。格式示例：

```json
{
  "source": "independent-vendor-specification",
  "layout_v1": {
    "rows": 1,
    "columns": 2,
    "ports": [
      {"id": "nic1-p1", "label": "NIC1 / P1", "row": 1, "column": 1, "slot_no": 1},
      {"id": "oob", "label": "OOB", "row": 1, "column": 2}
    ]
  }
}
```

行数1–16、列数1–64，端口1–256个；行列从1开始，ID与位置各自唯一，位置不得越界。`slot_no`可省略；填写时必须引用同一版本槽位，不能为null，不把缺失槽位推断为板载或某个默认角色。省略`layout_v1`继续保留旧JSON元数据，但显示未登记可预览布局；声明该字段却无效时拒绝扫描导入和发布。额外元数据原样保留。

审核弹窗随输入预览，位置冲突或失效引用阻断发布；历史版本各自读取自身布局和槽位，可用键盘选择端口查看标识、行列、PCIe位置、期望NIC及默认角色。默认角色明确作为型号预期，不冒充项目RoleBinding、链路up/down或真实端口监控。新版本不改旧布局/设备绑定，不实现设备重绑定、门禁失效或完整PortPanel监控视图。无数据库迁移。


## 硬件校验复用物料身份解析

逐实体BOM的GPU/NIC数量、槽位和正式型号比较，按物料写入解析后的machineUID归属，不再分别收集所有同名SN/行号/机器UID。引用优先级继续为item_uid、包内bom_line_no、业务码；例如第一台SN为20但行号为1、第二台行号为20，部件parent_sn=20属于第二台，不能重复计入第一台。MAC前缀同样使用已解析归属。结构/引用错误先BLOCK；身份解析成功后才对比硬件期望，提交会重复全部检查。宽表仍拒绝用MAC证明NIC/GPU物理库存。


## 项目资产查看固定型号

资产列表正式返回model_id、model_version_id和绑定版本号，资产记录version单独保留。`GET /api/v1/projects/{id}/assets/{assetId}/model`按资产主键及项目同时定位，只读返回完整不可变版本和槽位；退役历史仍可读，库内新版本只提示可见的新版本号，不替换绑定。查询不读取Machine当前型号投影，不回退latest。

项目成员可从资产页“查看绑定型号”读取固定布局、规格和版本摘要；全局共享型号通过项目授权边界读取，项目私有型号不得跨scope泄露。缺失绑定、不匹配的型号/版本、异项目资产或无权项目均不可读取；列表对不合法scope不暴露型号详情并显示未绑定已发布型号。弹窗只读，按用户/项目/资产/版本隔离缓存，项目切换销毁原资产弹窗状态。完整型号JSON是独立期望，不是G1或真实链路结果；没有新增绑定修改、门禁或迁移流程。
